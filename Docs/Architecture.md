# 架构与拍板记录

> 立项 2026-08-31。本文件记录架构决定和它们的理由,新决定追加在末尾的变更记录里。
> 规划稿、里程碑排期在本地 `Plan/`,不入库。

## 1. 一个账本,三张脸

任务、剧情进度、对话表面是三个功能,底下共用一个 **fact 账本**(业界叫 fact system,Valve 的对话系统、
巫师系列的 FactDB 都是这个底子)。

- **对话** = 读账本(条件分支)+ 写账本(选项后果)
- **任务** = 盯着账本若干条目的观察者,凑齐了打勾、广播事件、再记一笔
- **剧情进度** = 账本上几个大开关,决定世界处于哪个阶段

所以 `DreamNarrativeCore` 是账本 + 表达式 + 事件总线,Story 和 Stage 都是薄壳。三者互通因此是天然的:
任务完成度可以出现在对话条件里,对话选择可以推进章节。反过来做成三个各自存状态的孤岛,后期"对话里判断
任务状态"会逼得到处打洞。

**推论:插件的全部状态只住在 Core 一处。** 存档和联机因此只需要对付一个东西。

### 与 push 模型的区别

条件不是任务实例里的命名计数器、由游戏代码点名更新(那是 push 模型,`DreamGameplayTask` 走的路);
条件是表达式,fact 一变自动重估,游戏代码只写账本、不认识任何任务。进度数据集中在账本里,不分散在任务
实例里。

## 2. 文本是唯一真相

DSL 源文件是真相,资产是编译产物,图形编辑器是投影 —— 图上改一笔,直接写回源文件(保注释、保格式)。

理由:双向同步(资产是真相、文本是进出口)需要内容指纹、手改检测、Revert/Adopt 一整套机制,是
DreamShader 上真实付出过的代价。而这是全新系统,没有存量资产要迁移,连 decompiler 都可以不做。
副作用是 git 里永远是可读 diff。

**因此保格式的写回引擎(printer)是全项目最贵、最关键的一块地基**,图形编辑器的一切都盖在它上面。它要
配往返测试(parse → print → parse 等价性)。

## 3. 语言

- 表达式为叙事场景全新设计,不与 DreamUILang 对齐;但一仓之内 Story 与 Stage 必须共用同一套。
- **标识符一等公民支持中文**。fact 名会是"换水状态""墨梅册",台词全是中文,叙事 DSL 不支持 Unicode
  标识符等于自废。关键词保持英文,与 Dream 系列一致。
- 词汇同时覆盖解谜叙事向(章节、记忆链、闭环对白)与传统 RPG 向(任务日志、目标、步骤、奖励、主支线)。
- 诊断码前缀 `DNS`,码表见 `Docs/Diagnostics`。两条轨(parser / generator)的诊断载体分别用 FText 和
  FString,不要试图合并。

## 4. 静态校验就是 QA

单人开发没有 QA,校验器就是 QA。能查的:死链、不可达分支、孤儿证据、未声明的 fact、章节可达性、记忆链
可完成性、本地化 key 撞车。

**前提:校验器必须看得见所有人怎么改账本。** 只要有一处 C++ 偷偷 set fact,可达性分析就是假的。因此
fact key 集中声明,并标明归谁写 —— 叙事侧写的,还是游戏系统喂的(`extern` 声明)。这是全部校验能力的
地基。

## 5. Story 与 Stage 的边界

分界线就是巫师的逻辑层 / 表演层分界:ScreenPlay + FlowGraph + FactDB 对应 Story,Timeline 对应 Stage。

两者的接口只有一样东西:**稳定 ID**。演出按行 ID 挂在叙事上,谁也不含谁。因此可以单独启用、单独上架。

### 稳定 ID 的三重身份

对话行 ID 同时是:存档 key、本地化 key、Stage 演出的挂点。因此:

- 名字即 ID,但必须配改名迁移(redirect 表),否则上线后改个任务名就毁档;
- 每句对话第一天就是"稳定 ID + FText",编译进资产时用 `AsLocalizable_Advanced` 注册。自定义文本格式
  接不进 UE 的源码采集(采集宏名表硬编码在引擎里),但产物是资产就能吃标准 package 采集。这条不提前铺,
  翻译工作流是推倒重来级别的返工。

## 6. 时间基:VO 是权威

来自巫师3 的 Timeline Scaling:8 种语言配音长度不同,同一句话英语 12 秒、法语 14 秒,K 好的动画换个语言
全错位。他们的解法是每个表演事件的起点和长度都存成**相对该句 VO 的百分比**,不存绝对秒数。

因此:

- 对话行第一天就有 voice 引用 + 时长槽(空 = 按字数估算),播放功能后置;
- 对白演出的时序一律用百分比时间基;大招演出这类时序权威是动画的,才用绝对秒。

## 7. 静态定义与动态状态彻底分开

资产只描述"任务/对话长什么样",玩家进度全部住在存档结构里,靠 ID 对上。任何"把运行时状态写回资产"的
念头都是两份真相的开端。

## 8. 调试传送是刚需,而且影响数据设计

测第八章不能靠人肉打通前七章。要做"一键跳到任意剧情点",就要求每个章节/阶段在定义时**声明入场时账本应该
长什么样**(implied facts),跳转时自动补齐。这个字段第一天进 schema,后补很痛。

## 9. 联机:形状预留,不实装

账本按 server-authoritative 的形状设计(谁有权写、复制边界进 schema),第一版只跑单机。卖外部迟早被问到,
预留成本低,回头改账本层成本高。

## 10. 插件不带 UI

对话框、任务日志是纯接口 + 事件,项目自己画。DreamGUI 适配层将来作为可选模块,走 DreamMap 那种可选依赖
模式。演示用的临时 UI 放测试项目,不进插件本体。

## 11. 引擎与 Gameplay 模块

底座全自研轻量,不押 StateTree(5.8 authoring API 有版本漂移风险,而且对话是"停下来等输入"的图、任务是
一堆并行观察者,都不是状态树的自然形状)。流程节点将来可以留 StateTree 挂载点。

| 模块 | 关系 |
|---|---|
| GameplayTags | 账本 key;编译期可把 ID 注册成 tag。核心直依 |
| EnhancedInput | Stage 的输入锁、对话选择路由。直依 |
| LevelSequence | 三个接触点:嵌入播放(早)、相机轨单向导入(晚)、event track 反向触发。直依播放包装层 |
| Niagara | Stage 的 vfx 轨。直依;引用 `.dfs` 是 DreamFX 增强 |
| GAS | 独立适配模块:tag/GameplayEvent → fact,任务完成 → GameplayEvent,ability 触发 stage |
| SaveGame | 不强制自带存档文件:给账本快照结构 + 序列化接口 |
| Sequencer | 不做 Stage 的主载体(绑定重定向、REINST、toolkit 生命周期的坑;其编辑器时假设与"每角色一份、
运行时重定向、可被打断"拧着),自写轻量 evaluator |

## 12. 与 DreamGameplayTask 的关系

`DreamGameplayTask`(BP 向任务框架,5.0–5.6,已发布 v3.1.0)与本插件是 push / observe 两种模型,**不桥接**
—— 桥了就是任务进度两个真相、存档两套。三个角色:

1. **需求清单**:它的功能集(条件模板、超时、子任务链、优先级、调试器)是经用户验证的真实需求,本插件的
   RPG 任务词汇照此对齐;
2. **器官捐献者**:状态机语义、Handle 生命周期、Debugger 面板骨架直接搬来重铸;
3. **迁移目标**:它作为独立 BP 产品继续活在通用市场,本插件出可选迁移工具(任务定义 → DSL)。
